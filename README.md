# Search (search:) Discipline Dictionary

The Search dictionary provides a small set of high-level, human-meaningful
keywords that describe *what a data set is about* — the science discipline, the
target, how the data were collected, and the research context behind them. Its
purpose is findability: giving search tools and people browsing the archive a
consistent vocabulary to filter on, rather than adding new science metadata to
individual observations.

Because it describes a data set as a whole, this dictionary is intended for
**bundle and collection labels**. Applying it to individual products is possible
but is not the design target — a bundle-level statement like "surface geology,
asteroids, spectroscopy" is what makes an archive searchable, and repeating it
on every product adds noise without adding information.

Every attribute is free text with a suggested vocabulary. Nothing is a
schema-enforced enumeration, and everything is optional and repeatable, so a
label author fills in what is true and skips the rest.

# About This Repository

The distinguishing feature of this repo is that the *IngestLDD* is **generated**.
The authored source of the dictionary is a YAML model —
[internal/src/search-ldd-model.yaml](internal/src/search-ldd-model.yaml) — which
expresses the class hierarchy, definitions, and suggested vocabularies in a form
that is easy to review and edit. The same model drives the IngestLDD, the web
form, and the PDF form, so those three never drift apart.

```
internal/src/search-ldd-model.yaml
        |
        +--> internal/tools/yaml_to_ldd.py     --> src/PDS4_Search_IngestLDD.xml --> (LDDTool) --> build/
        +--> internal/tools/build_web_form.py  --> dist/web-form.html
        +--> internal/tools/generate_pdf_form.py --> data_dictionary_form.pdf
```

In this repo you will find...

* **[src](src)/** - The managed *IngestLDD* file that defines this namespace.
  It is generated from the YAML model; treat it as a build product that happens
  to be checked in, since PDS build automation reads it from here.
* **[internal](internal)/** - The authored model and the tooling that turns it
  into the artifacts above. See [internal/tools/README.md](internal/tools/README.md).
* **[build](build)/** - Files generated by the build process: schema files used
  in designing and validating labels, JSON for inclusion in code, and LDDTool
  report files. Development and release versions live in separate subdirectories.
* **[dist](dist)/** - The built single-file web form, published to the docs site.
* **[docs](docs)/** - Sphinx sources for the documentation site.
* **[test](test)/** - Regression tests, in the form of documented labels.
* **[logs](logs)/** - Logs from the automated LDDTool and Validate runs.
* **[.github](.github)/** - Workflow definitions for the automated builds.

Merge final changes to documentation and LDD structure into `main`. Pushing to
`main` rebuilds the documentation site and deploys it straight to GitHub Pages
as an Actions artifact — there is no generated branch to avoid editing.

# Working on the Dictionary

## Editing the model

Edit `internal/src/search-ldd-model.yaml`. The structure is recursive: a key with
a `children` list is a class, and a key without one is an attribute.

```yaml
Scientific_Discipline:
  definition: Information about the scientific discipline and research context.
  children:
  - Study_Focus:
      definition: High-level research focus.
      examples:
        Surface: Study focused on planetary geology such as features or properties
        Composition: Study focused on chemical or mineral composition
```

`examples` are suggested values with their meanings. They populate the forms and
the documentation, but they are *not* emitted as permissible values — the
generated attributes are open `ASCII_Short_String_Collapsed` fields, so a label
author can supply a value the model has not anticipated. Class and attribute
names are normalized on the way out (`Study_Focus` becomes the `study_focus`
attribute), so YAML keys can stay readable.

## Regenerating the IngestLDD

```bash
python internal/tools/yaml_to_ldd.py src/PDS4_Search_IngestLDD.xml
```

`compile_model.py` does the actual YAML-to-dictionary transform and is shared by
every generator, so a change to naming or association rules lands in all of them
at once.

## Building the dictionary

Each build is auto-generated by GitHub Actions using PDS4 LDDTool and the
Validate Tool — see [.github/workflows/ldd-ci.yml](.github/workflows/ldd-ci.yml).
Pushing a change under `src/` on any branch other than `main` triggers a build
against every version listed in [pds4_versions.txt](pds4_versions.txt), then
commits the generated LDDs and execution logs back to the branch.

To build locally, install
[LDDTool](https://nasa-pds.github.io/pds4-information-model/model-lddtool/index.html)
and run:

```bash
lddtool -lpsnJ src/PDS4_Search_IngestLDD.xml
```

## Building schemas for older information model versions

Archive labels in the wild are pinned to a range of PDS4 information model
versions, and a Search schema has to exist for each one before those labels can
be validated. `build_search_ldd_schemas.py` builds the namespace against a
specific IM version:

```bash
python internal/tools/build_search_ldd_schemas.py
```

# The Keyword Forms

Filling in fifty-odd optional keywords by hand-editing XML is unpleasant, so the
model is also published as two forms.

## Web form

[build_web_form.py](internal/tools/build_web_form.py) generates `data.js` from
the compiled model, builds a React/Vite app from
`internal/src/web/template`, and emits a **single self-contained HTML file** at
`dist/web-form.html` (via `vite-plugin-singlefile`). No server, no build step for
the reader — the docs site serves that one file, and it also works from a local
copy or a thumb drive.

```bash
python internal/tools/build_web_form.py
```

Selections are encoded into the URL so a partly-filled form can be shared or
bookmarked. Rather than serializing names, the form encodes the choices as
bitfields against a *mapping file* — `internal/src/web/web_form_mapping_vN.json`
— which pins the sorted order of every class, attribute, and example value. The
bitfield is then compressed with `lz-string` and shown as both a link and a QR
code. The build compares the newly compiled model against the latest mapping and
cuts a new version only when the vocabulary actually changes.

**Known limitation: URLs are not version-safe across mapping changes.** The
encoder stamps the mapping version into the payload as `ver`, but the form
bundles only the newest mapping and the decoder never reads `ver` back
(`expandCompressedState` in `src/utils/bitfield.js`). A URL generated under an
older mapping will therefore be decoded against the current index order, and if
that order shifted it will silently resolve to the wrong classes, attributes, or
values — no error, just different answers. The older `web_form_mapping_vN.json`
files are retained on disk but are not consulted at runtime.

Two consequences. Treat shared form URLs as short-lived working state rather
than durable records, and keep the old mapping files around — making decoding
honor `ver` is the fix, and those files are the only record of what the earlier
index orders were.

## PDF form

A printable worksheet, for use in workshops and interviews where a browser is not
the right tool. It lists every class and attribute with its definition and a
blank field to write the value in. Note that it does *not* print the suggested
vocabularies: the generator offers checkboxes only for enumerated attributes, and
this dictionary deliberately has none, so every attribute prints as a write-in
field. Anyone filling one out needs the reference documentation beside them.

```bash
python internal/tools/generate_pdf_form.py
```

This writes `data_dictionary_form.pdf` in the repository root. It needs
`reportlab` and `pyyaml`.

# Generating Namespace Documentation

The documentation website is managed by GitHub Pages. When changes land on
`main`, [build-docs.yml](.github/workflows/build-docs.yml) rebuilds the web form,
runs Sphinx, and deploys the result. The docs build depends on
`dist/web-form.html` existing — `make github` asserts this — so the web form is
rebuilt in CI before Sphinx runs.

To build the site on your own system:

1. Clone the repository
2. Install Python dependencies (preferably within a Python virtual environment[^1]):
```
pip install -r docs/requirements.txt
```
3. Follow the steps below

[^1]: [Python Virtual Environment How-To at docs.python.org](https://docs.python.org/3/library/venv.html)

## To Generate HTML

1. Build the HTML documents
```
cd docs
make clean html
```
   Note that in Windows environments you will need to run the "clean" and "html" operations as separate invocations of "make":
```
cd docs
make clean
make html
````

2. Preview the HTML in your browser
```
open build/html/index.html
```

Note that `make github` is the target CI uses to publish, and it *deletes* the
non-docs directories in the working tree before copying the built site into the
repository root. Use `make html` locally.

## To Generate PDF

1. Install some additional dependencies:

   On a Mac:
   ```
   brew install texlive
   ```

   On Linux:
   ```
   apt-get install texlive-latex-recommended texlive-latex-extra texlive-fonts-recommended
   ```

2. Make the PDF
```
cd docs
make latexpdf
```

The output PDF will be written into the *docs/* directory.
The output file name will depend on the value for the ```project``` variable
in the *docs/source/conf.py* file.

# Contributing to this Dictionary

## Suggest a Feature or Report a Bug

There is a common place to request enhancements and report problems for
any PDS-curated dictionary - the [PDS4 Issue Repo](https://github.com/pds-data-dictionaries/PDS4-LDD-Issue-Repo/issues/new/choose).
Search for the \[ldd-search\] update request block and click the green
"Get Started" button.

Requests to add a keyword to a suggested vocabulary are welcome and are usually
the easiest kind of change to make — say which attribute it belongs under and
what it means.

## Contribute Code or Documentation

If you'd like to actively contribute to development, begin with the
feature/bug process described above. Then familiarize yourself with
the [LDD Update Process](https://pds-data-dictionaries.github.io/development/ldd-update.html)
and contact the dictionary steward to coordinate development, testing,
and release. And thanks!
